# Worksheet Pipeline 개발 계획 (v2, 2026-11-23)

> **읽는 법**: 이 문서는 날짜별 기록이라 앞 절에 낡은 결정이 남아 있다. 2026-11-23 토스트 대표 협의 이후에는 §11 마지막의 '협의 후 구현 반영' 절이 앞 절보다 우선한다. 바뀐 것: 프레임 기준 24FPS → **29.97**, 요약은 시트 맨 아랫줄과 Summary 시트 → **'요약' 탭 하나**, 방영 길이·목표 컷 수를 **고정 입력**으로 받아 합계와 견줌, 에셋 확인은 공란이어도 **승인을 막지 않음**, 용어는 저장소 루트의 `CONTEXT.md`를 따름. 낡은 문장에는 취소선 대신 `[폐기]`를 붙였다.

## 1. 목적

- PD가 시나리오(원작 대본)와 스토리보드(콘티)를 올리면, 컷 분할·썸네일·에셋을 거쳐 Google Sheet Worksheet가 새로 생성됨
- PD 작업은 승인 2회로 한정. 작업자 배정과 작업 결과 입력은 PD가 시트에서 직접 진행(Agent는 목록만 제공)

## 2. 업무 흐름 (사용자 지시 반영)

| 순서 | 단계 | 주체 | 산출 | 저장 위치 |
|---|---|---|---|---|
| 1 | Agent 호출 | PD | 콘솔 artifact 게시 | artifact |
| 2 | 업로드 탭에서 docx, PDF 올림 | PD | 입력 2종 | Drive `EPxx/00_입력` |
| 3 | 컷 분할 | 플러그인 | 컷 목록(ID, 지문, 대사, Cam Move, 분할안) | Drive `EPxx/02_작업/cuts.json` |
| 4 | 썸네일 생성 | 플러그인 | 컷별 이미지 | Drive `EPxx/02_작업/thumb/` |
| 게이트 1 | 컷·썸네일 확인 탭에서 승인 | PD | 승인 기록 | artifact db |
| 5 | 에셋 확정 (BG·CH·PR) | 플러그인 제안, PD 확정 | Asset 목록 | Drive `EPxx/02_작업/assets.json` |
| 게이트 2 | 에셋 확인 탭에서 승인 | PD | 승인 기록 | artifact db |
| 6 | Google Sheet 생성 | 플러그인 | 시트1(EP), Asset 시트, 요약 탭(Summary 시트는 [폐기]) | Drive `EPxx/01_산출` |
| 7 | 결과 탭에서 위치·요약·검증 확인 | PD | 시트 링크, 요약 | artifact |

- 승인 전에는 시트가 만들어지지 않음. 기존 시트는 덮어쓰지 않고 새 파일로만 생성

## 3. artifact 구성 (콘솔 1장, 탭 4개)

1. 업로드: docx, PDF 슬롯 2개. 파일명, 크기, 버전, 저장 상태 표시
2. 컷 확인: 컷 카드(썸네일, 지문, 대사, 분할안). 수정·승인
3. 에셋 확인: BG·CH·PR 목록, 컷별 사용 현황. 코드 지정·승인
4. 결과: Google Sheet 링크, 시트 안 위치(탭, 행 범위), 요약 탭 안내, 검증 결과 (맨 아랫줄 요약은 [폐기])

- 실행 상태와 승인 기록은 artifact db에 두고, 플러그인이 읽고 씀
- 요약 값(총 컷 수, 총 Sec·Frame, 분류별 건수)은 `summary.json` 한 곳에서 계산해 요약 탭과 결과 탭에 같은 값으로 기록 (시트1 맨 아랫줄은 [폐기])

## 4. 레퍼런스에서 확인한 사실 (EP12)

- docx: 컷 ID와 표가 없고 컷당 한 단락. 지문과 대사가 붙어 있음. 머리말에 "총 166컷 = 중복 연출 32컷 제외, 134컷"
- PDF: 51쪽, 컷 번호 `C01` 형식, TIME 칸 비어 있음, 24FPS 표기, 약 45.5MB
- 정답 시트: 컷 행 179개(`C001~C166` + 분할 a/b/c 13행, `C086_CH` 포함), 썸네일 174장, 29.97 기준 Sec 수식, Start Frame 모두 101, 하단 합계·완료율 수식(범위 `2:180`, 완료율 `/177` 하드코딩)

## 5. 확인 필요 (미결)

1. 166(원작)과 179(분할 후 행 수)의 관계, "134컷·중복 연출 32컷"의 뜻
2. 프레임 기준 24 / 29.97 → **해결: 29.97** (2026-11-23 협의)
3. Sec, Frame, Start/End Frame의 입력 주체(입력 자료에 없음)
4. 컷에 콘티 칸이 여러 개일 때 썸네일 선택 규칙(기본안: 첫 칸)
5. `RP`는 시트의 `PR`(Prop)로 진행
6. 업로드 한도: artifact 바이너리 파일 한도(약 15MB)가 PDF(45.5MB)보다 작을 수 있음. PoC에서 확인하고, 초과 시 PDF 이미지 다운샘플 또는 Drive 직접 업로드 링크로 대체

## 6. Harness

1. 결정적 계산(Frame, Sec, CH_Count, 합계, 범위)은 스크립트와 수식. LLM은 컷 분할과 에셋 추출 제안만
2. 게이트 2개. 승인 기록이 없으면 hook이 시트 쓰기를 차단
3. 자동 검증: 모든 BG·CH·PR 코드가 Asset에 존재, 컷 ID 중복 없음, 원작 컷 수·최종 행 수 대조, 대사 수 대조, 수식 범위가 전 행 포함, 세 곳의 요약 값 일치
4. 평가: EP12 정답 시트와 B~N열을 대조(컷 ID 일치율, CH·BG·PR 일치율, 썸네일 매칭률)
5. 실행 기록(입력 파일 버전, 승인 시각, 검증 결과)을 요약 탭 하단에 기록

## 7. 플러그인 구성

- skills: `worksheet-intake`, `cut-split`, `thumbnail`, `asset-build`, `worksheet-build`, `worksheet-verify`
- agents: 컷 파서, 독립 검증자
- scripts(Python): docx 파싱, PDF 칸 추출, 프레임·합계 계산
- hooks: 기존 시트 덮어쓰기 차단, 승인 전 쓰기 차단
- `.mcp.json`: Google Drive, Google Sheets 커넥터
- artifact: 콘솔 1장

- 썸네일 방식: "시트에서 바로 보임"과 "공유 설정 단순함"을 함께 얻기 어려움

- docx에 컷 ID가 없어 PDF와 순서·대사로 매칭. 연출이 바뀐 컷은 불확실 표시
- 프레임 기준을 잘못 정하면 Sec 합계 전체가 틀림
- 공정 열의 TK 일정은 EP마다 달라 템플릿 변수로 두고 PD가 입력

### 결정: 원본 PDF는 Drive 동기화 폴더로 복사 (2026-11-23)

- 이 PC의 `G:\내 드라이브`는 Drive 데스크톱 동기화 폴더. 플러그인이 로컬 파일 복사로 원본 PDF를 `EPxx/00_입력`에 넣음(커넥터 10MB 한도 우회)
- 시험: 원본 PDF(45.5MiB)를 `G:\내 드라이브\worksheet-pipeline_PoC (삭제 가능)\`에 복사 성공. 복사 후 약 1분 안에 Drive 커넥터 검색에서 같은 크기(47,713,424바이트)로 조회됨. 즉시 반영은 아니므로 플러그인은 복사 후 검색으로 반영을 확인한 다음 다음 단계로 진행
- 흐름 변경: 업로드 탭의 docx와 PDF 130dpi 사본은 artifact(20MiB 한도)로 받고, 플러그인이 원본 PDF를 PD 로컬 경로(Drive 동기화 폴더)에서 `00_입력`으로 복사. PD 환경에 Drive 데스크톱이 없으면 이 경로를 쓸 수 없으므로, 플러그인 시작 시 `G:\` 동기화 여부를 점검하고 없으면 PD 직접 업로드로 안내
- 제약: 동기화 폴더 복사는 로컬 PC에서 실행될 때만 가능(Claude Code·Cowork 로컬 세션). 클라우드 세션에서는 불가

### 결정: 시나리오 입력 형식과 컷 번호 규칙 (2026-11-24)

- 읽는 형식: .docx, .pptx, .txt, .md. 구현은 `plugin/scripts/parse_docx.py`의 `paragraphs()`이고, `scenario_meta.py`도 같은 함수를 쓴다.
- 컷 번호 규칙: docx는 번호 매기기 목록(가장 많이 쓰인 목록이 본문)이다. 나머지 형식은 줄 앞의 `12.`, `12)`, `C012`가 컷 번호이고, pptx는 글머리 자동 번호도 컷 번호로 본다. `12.5분`, `10:30`은 번호로 보지 않는다.
- 번호가 없으면 "컷 번호 목록을 찾지 못했습니다"라는 오류를 낸다. txt는 UTF-8과 CP949를 읽는다.
- 검증: EP12 docx에서 만든 txt·md·pptx 시험본이 모두 166컷이고 제목·목표 컷 수가 docx와 같다. 실제 txt·pptx 시나리오로는 아직 확인하지 않았다.
- 한계: 번호가 없는 자유 서식 시나리오는 컷으로 나누지 못한다. 그런 파일은 원작사에 번호 목록을 요청한다.

### 결정: 회사별 작업 폴더 지정과 폴더 자동 생성 (2026-11-24)

- 저장 위치는 고정 경로가 아니라 **회사마다 지정하는 작업 폴더**다. 콘솔 상단 "Google Drive 연결 설정" 패널에서 폴더 링크를 붙여 넣고 읽을 수 있는지 확인한다. 위 표의 `EPxx/…` 경로는 모두 이 작업 폴더 아래를 뜻한다.
- 구조: `<작업 폴더>/<애니메이션명>/<에피소드 번호>/00_입력·01_산출·02_작업`. 애니메이션명·에피소드 폴더는 미리 없어도 된다.
- 가능 여부: 확인함. Drive 커넥터 `create_file`이 폴더 종류(`application/vnd.google-apps.folder`)와 `parentId`를 받으며, PoC에서 폴더 생성이 정상 동작했다.
- 구현 원칙
  1. **찾고 없으면 만든다.** 폴더를 만들기 전에 같은 이름이 상위 폴더 안에 있는지 `search_files`로 찾고, 있으면 그 폴더를 쓴다. 이렇게 하지 않으면 같은 에피소드를 다시 돌릴 때 폴더가 둘로 갈라진다.
  2. **만드는 주체는 플러그인이다.** 콘솔은 `search_files`·`get_values`만 승인받아 폴더를 만들 수 없다. 콘솔이 직접 만들려면 `create_file` 승인을 추가해야 하며, 사용자의 쓰기 승인이 하나 늘어난다.
  3. **쓰기 권한은 폴더 확인으로 알 수 없다.** 현재 "폴더 확인"은 읽기만 점검한다. 읽기 전용 폴더도 통과하므로, 1단계 확인 직후 에피소드 폴더를 만드는 시점에 쓰기 실패를 잡아 이유를 안내한다.
  4. **폴더 이름은 담당자가 확인한 값만 쓴다.** 애니메이션명(파일 이름에서 추정)과 에피소드 번호는 1단계 담당자 확인 체크를 마친 뒤에만 폴더 이름으로 쓴다. 철자가 한 글자만 달라도 새 폴더가 생기기 때문이다.
- 미구현: 폴더 생성 코드, 쓰기 권한 안내, 회사 목록 저장(지금은 링크를 붙여 넣는 방식이며 브라우저에 마지막 링크만 기억한다).
